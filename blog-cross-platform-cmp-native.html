양대 플랫폼(iOS/Android)을 지원하는 최선의 방법?

"하나의 코드로 두 마리 토끼를 잡으려다 마주치는 한계, 그리고 내가 'KMP(Data/Domain) + Native(Presentation)' 조합을 선택한 이유"

작성자: 이강호 (Kano — 모바일 개발자)

"이번 신규 프로젝트, iOS랑 안드로이드 둘 다 빠르게 내야 하는데 어떤 기술 스택으로 가야 할까?"

모바일 서비스를 만드는 개발자라면 누구나 한 번쯤 밤잠을 설치며 고민해보았을 질문입니다. 비즈니스의 빠른 시장 검증을 위해서는 iOS와 Android 양대 플랫폼을 모두 지원해야 하지만, 혼자 혹은 소수의 인원으로 두 OS를 각각 처음부터 개발하는 것은 비용과 시간 면에서 너무나 큰 부담이기 때문입니다.

이때 자연스럽게 가장 먼저 손이 가는 선택지가 바로 Flutter나 React Native 같은 크로스 플랫폼 프레임워크입니다. "하나의 코드베이스로 두 플랫폼을 동시에 지원할 수 있다"는 약속은 개발자에게 거부하기 힘든 달콤한 유혹입니다.

하지만 현업에서 직접 부딪히며 앱을 개발하고 유지보수하면서 깨달은 것은, 모든 은총알(Silver Bullet)에는 반드시 현실적인 대가가 따른다는 점이었습니다.

"비즈니스 로직의 중복은 없애고 싶지만, 유저가 매일 손끝으로 만지는 네이티브 특유의 정교함과 메모리 효율, OS 신기능 지원을 포기할 수는 없다. 과연 양대 플랫폼을 지원하는 진정한 최선의 방법은 무엇일까?"

1. 크로스 플랫폼(Flutter, RN): 분명한 장점과 현실적인 한계

Flutter와 React Native는 현대 소프트웨어 생태계에 지대한 공헌을 한 훌륭한 도구들입니다. 저 역시 빠른 MVP 검증이나 1인 프로젝트에서 적극적으로 활용해 보았고, 특유의 빠른 개발 생산성에 감탄하기도 했습니다.

장점: 압도적인 출시 속도와 단일 코드베이스

  • Write Once, Run Everywhere: UI부터 비즈니스 로직까지 하나의 언어(Dart 또는 JS/TS)로 작성하여 두 플랫폼에 즉시 빌드할 수 있습니다.
  • 동일한 개발 사이클: 두 플랫폼 간의 기능 배포 일정 차이가 사라지고, 적은 인력으로도 빠르게 프로토타입을 완성할 수 있습니다.

하지만 서비스의 규모가 커지고, 복잡한 사용자 인터랙션과 고도화된 시스템 기능이 요구되는 단계에 들어서면 다음과 같은 구조적 한계를 체감하게 됩니다.

한계 ①: 무거운 메모리 풋프린트와 런타임 오버헤드

크로스 플랫폼 앱은 순수 네이티브 앱에 비해 기본 메모리 사용량이 필연적으로 높습니다.

  • Flutter: 앱 바이너리 내에 Dart 가상머신(VM)과 자체 그래픽 렌더링 엔진(Skia / Impeller)을 통째로 패키징합니다. 텍스트 몇 줄만 있는 빈 화면을 띄우더라도 기본적으로 상당한 메모리를 점유하며, 복잡한 대량 리스트 스크롤이나 대용량 이미지 처리 시 가비지 컬렉터(GC) 동작에 따른 미세한 프레임 드랍(Micro-jank)이 발생하기 쉽습니다.
  • React Native: JavaScript 런타임(Hermes 등) 구동 오버헤드와 JS-Native 간의 비동기 통신(또는 JSI) 비용으로 인해 CPU 연산과 메모리 압박이 가중되며, 이는 배터리 소모와 기기 발열로 직결됩니다.

한계 ②: '가짜 네이티브'의 장벽과 OS 고유 기능 지원의 지연

Apple과 Google은 매년 WWDC와 Google I/O를 통해 각 OS만의 혁신적인 신기능을 쏟아냅니다:

  • iOS: Dynamic Island, Live Activities, 락스크린 위젯, ProMotion(120Hz) 가변 주사율, 정교한 햅틱 엔진, Apple Intelligence API
  • Android: Material You 동적 테마, 예측 뒤로가기(Predictive Back), 세분화된 포그라운드 서비스 및 배터리 최적화 정책

크로스 플랫폼은 이 혁신을 Day 1에 온전히 흡수하지 못합니다. 제3자 오픈소스 플러그인이 나오기를 마냥 기다려야 하거나, 결국 각 플랫폼에 맞춰 MethodChannel이나 네이티브 브리지를 직접 작성해야 합니다.

"결국 네이티브 기능을 쓰기 위해 각 OS 코드를 따로 짜고 있다면, '하나의 코드로 개발한다'는 크로스 플랫폼의 본래 약속은 어디로 간 것일까요? 배보다 배꼽이 더 커지는 딜레마에 빠지게 됩니다."

2. 내가 선택한 해답: KMP + Native 하이브리드 전략

양대 플랫폼을 지원하면서 개발자인 우리가 진정으로 원했던 가치는 무엇이었을까요?

"서로 다른 두 OS의 화면(UI)을 억지로 붕어빵 찍듯 똑같이 만드는 것"이 아니었습니다. 진짜 우리가 해결하고 싶었던 비효율은 "네트워크 통신, 로컬 DB 캐싱, 비즈니스 검증 규칙, 데이터 가공 로직을 iOS와 Android에서 두 번씩 따로 구현하고 버그를 맞추는 고통"이었습니다.

그래서 저는 가장 균형 잡히고 단단한 조합으로 KMP (Kotlin Multiplatform) + Native 전략을 채택했습니다.

핵심 아키텍처 원칙:
• Data Layer & Domain Layer: KMP (Kotlin Multiplatform)로 100% 공유
• Presentation Layer: 각 OS의 순수 네이티브(Jetpack Compose & SwiftUI)로 구현
💡 잠깐! KMP와 CMP, 무엇이 다르고 어떤 표현이 맞을까?

많은 분들이 KMP와 CMP를 혼용해서 사용하곤 합니다:

  • KMP (Kotlin Multiplatform): JetBrains가 만든 코어 기술/플랫폼입니다. 로직, 데이터 레이어, 네트워크, DB 등 비즈니스 코드를 Kotlin으로 작성하고 플랫폼별 네이티브 바이너리로 직접 컴파일합니다.
  • CMP (Compose Multiplatform): KMP 기반 위에서 동작하는 선언형 UI 프레임워크입니다. 화면(UI)까지 Compose 코드로 통일해서 렌더링하고 싶을 때 사용하는 기술입니다.

👉 결론: 우리가 취하는 아키텍처는 화면(UI)을 공통 캔버스에 그리는 것이 아니라 각 OS 고유의 네이티브(SwiftUI / Jetpack Compose)로 구현하고, Data와 Domain 로직만 공유하는 구조이므로 공식적으로 가장 정확한 표현은 KMP + Native입니다!

왜 이 조합일까요? 코틀린 멀티플랫폼(KMP)은 별도의 가상머신이나 자바스크립트 엔진을 띄우지 않습니다.

Android에서는 네이티브 JVM 바이트코드로, iOS에서는 LLVM 컴파일러를 통해 순수 Objective-C/Swift 바이너리 프레임워크(.xcframework)로 직접 빌드됩니다. 런타임 통신 브리지도 없고, 불필요한 메모리 낭비도 전혀 없는 진짜 네이티브 바이너리로 동작합니다.

3. 계층별 구현: Clean Architecture를 멀티플랫폼에 녹이다

모바일 KMP + Native 계층 구조 아키텍처 
┌─────────────────────────────────────────────────────────────┐
│                 PRESENTATION LAYER (NATIVE)                 │
│   Android: Jetpack Compose (Kotlin)   │   iOS: SwiftUI (Swift)   │
│   • 120fps 유체 애니메이션             │   • Dynamic Island / 위젯 │
│   • Material 3 인터랙션                │   • HIG 고유 햅틱 및 제스처│
└──────────────────────────────┬──────────────────────────────┘
                               │ StateFlow / ObservableObject
┌──────────────────────────────▼──────────────────────────────┐
│                  DOMAIN LAYER (KMP / SHARED)                 │
│   • UseCases (인증, 결제, 장바구니, 데이터 검증 로직)           │
│   • Domain Models & State Machine (MVI / Redux)             │
│   • 플랫폼 간 비즈니스 규칙 정합성 100% 일치                 │
├─────────────────────────────────────────────────────────────┤
│                   DATA LAYER (KMP / SHARED)                  │
│   • Network Client: Ktor Client (HTTP / WebSocket)          │
│   • Local Storage: SQLDelight / Room KMP                    │
│   • DTO Mapping & Repository Implementations                │
└─────────────────────────────────────────────────────────────┘

① Data & Domain: KMP로 완벽 일원화

  • 네트워크 및 캐싱: Ktor와 SQLDelight / Room KMP를 활용하여 API 통신 및 로컬 캐싱 엔진을 단일 코드로 구축합니다.
  • 도메인 정책: 유효성 검사, 결제 할인율 계산, 상태 머신(State Machine) 등 비즈니스 핵심 규칙을 하나의 코드로 관리합니다.
  • 결과: "iOS에서는 되는데 안드로이드에서는 결제 금액 계산이 다르게 나온다"와 같은 플랫폼 간 비즈니스 로직 불일치 버그가 원천 차단됩니다. 공유 로직에 대한 단위 테스트(Unit Test)를 한 번만 작성해도 양대 플랫폼 전체의 안정성이 검증됩니다.

② Presentation: 각 OS의 순수 네이티브 UI로 작성

  • Android (Jetpack Compose): Google의 최신 디자인 시스템(Material 3), 빠른 리컴포지션, Android 시스템 백버튼 및 제스처에 최적화된 화면을 구현합니다.
  • iOS (SwiftUI): Apple의 Human Interface Guidelines(HIG)를 충실히 반영한 네이티브 네비게이션, Dynamic Island, 실시간 활동(Live Activities), 잠금화면 위젯 등을 단 한 줄의 타협 없이 완벽하게 연동합니다.
  • 상태 구독: KMP 공통 모듈에서 방출되는 Kotlin의 StateFlow를 Android에서는 collectAsStateWithLifecycle()로, iOS에서는 Swift의 AsyncSequence나 @Published 래퍼를 통해 손쉽게 네이티브 상태로 바인딩합니다.

4. 기술 스택 종합 비교

각 접근 방식의 실질적인 트레이드오프를 표로 비교해 보면 KMP + Native 조합의 강점이 더욱 선명하게 드러납니다.

비교 항목 Flutter / React Native Full Native (각각 개발) KMP + Native (채택)
코드 공유율 85% ~ 95% (UI + 로직) 0% (완전 분리) 50% ~ 65% (로직/데이터 공유)
메모리 및 성능 VM/엔진 오버헤드로 다소 무거움 최상 (100% 네이티브) 최상 (런타임 오버헤드 제로)
OS 신기능 지원 플러그인 대기 또는 브리지 작업 필요 발표 당일 즉시 적용 가능 UI가 네이티브이므로 즉시 적용 가능
비즈니스 로직 정합성 단일 코드로 일치 플랫폼 간 오차/버그 발생 위험 높음 KMP 단일 코드로 완벽 보장
유저 사용 경험(UX) 미세한 제스처/물리엔진 이질감 존재 OS 고유의 가장 자연스러운 경험 100% 순수 네이티브 사용성 보장
개발자 경험 및 협업 특정 프레임워크 전담 학습 필요 iOS/Android 개발 분리 네이티브 전문성 유지 & 로직 공유

5. 한 명의 개발자로서 실무에서 체감한 현실적인 이점

이 아키텍처를 실제로 적용하며 개발자로서 가장 크게 체감한 부분은 기술적 수치뿐 아니라 개발 만족도와 유지보수의 편안함이었습니다.

① 네이티브 개발자로서의 전문성과 개발 재미 유지

크로스 플랫폼 도구로 넘어갔을 때 개발자로서 가장 답답했던 순간은 "내가 알고 있는 OS의 깊이 있는 최신 기능들을 프레임워크의 한계 때문에 온전히 써먹지 못할 때"였습니다. 반면 KMP + Native 구조에서는 Android에서는 Jetpack Compose의 모던한 기능을 마음껏 활용하고, iOS에서는 SwiftUI와 최신 Apple 생태계 기술을 타협 없이 깊이 파고들 수 있습니다.

② Kotlin과 Swift의 놀라운 시너지

현대의 Kotlin과 Swift는 문법적 구조와 언어 철학이 놀라울 정도로 닮아 있습니다. 또한 Jetpack Compose와 SwiftUI 역시 선언형 UI(Declarative UI)라는 동일한 패러다임을 공유합니다.

덕분에 iOS 개발자가 Kotlin으로 작성된 Domain UseCase 코드를 읽고 수정하는 데 진입장벽이 거의 없으며, 혼자 개발하더라도 두 플랫폼 사이의 컨텍스트 스위칭 비용이 획기적으로 줄어듭니다.

③ 비즈니스 변경에 흔들리지 않는 단단한 구조

API 스펙이 바뀌거나 결제/인증 등의 핵심 비즈니스 룰이 변경되었을 때, 공통 모듈의 코드를 한 번 수정하고 테스트를 돌리면 iOS와 Android 양쪽 모두에 완벽하게 일치된 로직이 즉시 배포됩니다. "안드로이드에서는 수정했는데 iOS는 깜빡했다"는 실수가 구조적으로 불가능해집니다.

6. 1인 개발자와 소규모 개발사 입장에서 왜 '신의 한 수'일까?

리소스가 극도로 한정된 1인 개발자나 소규모 개발사(스타트업, 에이전시)에게 기술 스택의 선택은 단순한 취향이 아닌 '생존의 문제'입니다.

처음에는 "혼자서 iOS/Android를 둘 다 만들어야 하니 무조건 Flutter나 React Native로 가야지!"라고 생각하기 쉽습니다. 하지만 첫 프로덕션 릴리즈를 거치고 6개월, 1년 이상 서비스가 운영 및 유지보수 단계로 넘어가면 전혀 예상치 못한 현실의 장벽에 부딪히게 됩니다.

이 관점에서 KMP + Native 구조가 왜 소규모 조직과 1인 개발자에게 실질적인 구원투수가 되는지 4가지 측면에서 짚어보고 싶습니다.

① 유지보수 부채의 50% 절감 (Single Source of Truth)

1인 개발자에게 가장 부족한 자원은 돈도 기술도 아닌 바로 '시간과 멘탈 에너지'입니다.

만약 순수 네이티브로 양대 플랫폼을 따로 만든다면, DTO 데이터 파싱, API 에러 핸들링, 로컬 캐시 DB 스키마 마이그레이션, 토큰 리프레시 로직, 결제 유효성 검증을 Swift와 Kotlin으로 두 번 똑같이 복사해서 짜야 합니다.

KMP를 활용하면 이 모든 복잡하고 버그가 숨기 쉬운 로직을 단 하나의 Kotlin 공통 모듈에서 끝낼 수 있습니다. 버그가 발견되어도 한 곳만 고치면 두 플랫폼 모두에 즉각 패치되므로, "Android는 고쳤는데 iOS는 잊어버려서 고객 문의가 빗발치는" 1인 개발자의 흔한 악몽에서 완전히 벗어날 수 있습니다.

② 서드파티 플러그인 호환성 지옥 탈출 (릴리즈 안정성)

크로스 플랫폼 앱을 혼자 운영해 본 분들이라면 누구나 한 번쯤 겪어본 악몽이 있습니다:

"매년 가을 새 iOS/Android 메이저 버전이 출시되었을 때, 사용 중이던 핵심 플러그인이 빌드 에러를 뿜어내고 오픈소스 메인테이너는 업데이트를 중단한 상황. 당장 앱스토어 심사를 올려야 하는데 오픈소스 C++이나 플랫폼 브리지 내부 코드를 혼자 디버깅해야 하는 막막함..."

대기업이라면 플랫폼 채널을 유지보수할 별도 엔지니어가 있겠지만, 1인 개발자나 소규모 팀은 그럴 여력이 없습니다.

반면 KMP + Native 구조에서는 UI와 시스템 API 연동 부위가 100% 공식 순수 네이티브입니다. Apple과 Google이 공식 배포한 가이드와 SDK를 그대로 가져다 쓰면 되므로, 제3자 라이브러리 메인테이너의 생사여탈권에 내 프로젝트가 인질로 잡히지 않습니다.

③ SwiftUI + Jetpack Compose: 혼자서도 가벼운 컨텍스트 스위칭

과거 UIKit(스토리보드/XIB)과 Android XML 시절에는 한 개발자가 두 화면을 넘나드는 것이 엄청난 인지 부하(Cognitive Load)를 주었습니다.

하지만 지금은 두 플랫폼 모두 모던 선언형 UI(Declarative UI)로 완전히 통일되었습니다:

  • State(상태)를 기반으로 UI를 리액티브하게 그리는 멘탈 모델이 90% 이상 일치합니다.
  • 오전에 Android의 LazyColumn과 Modifier로 컴포넌트를 설계했다면, 오후에 iOS의 LazyVStack과 ViewModifier로 옮겨 작성하는 과정이 놀라울 정도로 직관적이고 빠릅니다.

실제로 직접 개발해보면, UI를 따로 짜더라도 비즈니스 로직이 KMP로 완전히 묶여있기 때문에 화면을 구성하는 데 드는 시간은 전체 개발 일정의 극히 일부에 불과하다는 것을 체감하게 됩니다.

④ 소규모 개발사 / 외주 에이전시의 강력한 비즈니스 경쟁력

클라이언트 프로젝트를 수주하고 납품해야 하는 소규모 개발사 입장에서도 이 아키텍처는 독보적인 세일즈 포인트가 됩니다:

  • 견적 및 일정 경쟁력: 풀 네이티브 2벌 개발 대비 30~40% 단축된 개발 일정과 합리적인 견적을 클라이언트에게 제안할 수 있습니다.
  • 품질 타협 없는 100% 네이티브 감성: "크로스 플랫폼 특유의 버벅임이 있지 않을까?" 우려하는 클라이언트에게 100% 순수 네이티브 UI/UX 품질을 당당하게 보장합니다.
  • 하자보수 리스크 극소화: 납품 후 "안드로이드랑 아이폰에서 동작 규칙이 미세하게 달라요"라는 기능 불일치 클레임이 원천 차단되어, 사후 하자보수 비용으로 인한 프로젝트 적자 위험을 방어할 수 있습니다.

7. 솔직하게 짚어보는 KMP + Native의 단점, 그리고 그럼에도 채택한 이유

세상에 장점만 존재하는 기술은 없습니다. KMP + Native 구조 역시 실무에서 마주하는 분명한 허들과 단점들이 존재합니다. 솔직하게 이를 짚어보겠습니다:

단점 ①: UI 코드를 플랫폼별로 2번 작성해야 하는 공수

Flutter나 React Native는 단 한 번의 UI 작성으로 양대 플랫폼 화면을 끝냅니다. 하지만 KMP + Native는 Presentation Layer를 순수 네이티브로 두기 때문에, Android(Jetpack Compose)와 iOS(SwiftUI) 각각 뷰 코드를 2벌 작성해야 합니다.

단순 화면 개수가 수십, 수백 개에 달하는 대규모 뷰 중심 프로젝트라면, 화면을 그리는 절대적인 시간 자체가 크로스 플랫폼보다 더 소요되는 것은 명백한 사실입니다.

단점 ②: 초기 빌드 툴링 세팅과 Kotlin-Swift Interop 장벽

Android Studio와 Xcode 두 개발 환경을 모두 세팅하고, Gradle 빌드와 SPM(Swift Package Manager) 또는 CocoaPods 연동을 구성하는 초기 환경 설정 난이도가 다소 높습니다.

또한 Kotlin의 Coroutines / StateFlow, sealed interface 등을 Swift에서 자연스럽게 소비하기 위해서는 SKIE나 KMP-NativeCoroutines 같은 브리지 플러그인의 도움을 받거나 래퍼 코드가 필요하여, 처음 도입할 때의 러닝 커브가 존재합니다.

"그렇다면 이런 단점들이 명확한데도 왜 나는 KMP + Native를 최종 채택했을까?"

결론부터 말하자면, "초기에 감수해야 하는 단점들에 비해, 장기적으로 얻는 안정성과 유지보수의 장점이 비교할 수 없을 만큼 압도적으로 크기 때문"이었습니다.

이 단점들을 상쇄하고도 남는 결정적 이유 3가지:

  • 실제 개발 시간의 80%는 UI가 아니라 '비즈니스 로직과 데이터'에서 발생한다:
    경험이 쌓인 모바일 개발자라면 모두 공감할 것입니다. 서비스 개발에서 진짜 버그가 터지고 야근을 부르는 부분은 예쁜 버튼을 배치하는 UI 작업이 아니라, 복잡한 결제/주문 로직, API 응답 캐싱, 로컬 DB 트랜잭션, 토큰 갱신, 예외 처리입니다.
    현대의 선언형 UI(Compose/SwiftUI) 덕분에 화면 그리는 시간은 전체 개발 공수의 20~30%에 불과합니다. 가장 무겁고 위험한 70~80%의 비즈니스 로직을 KMP로 단일화했기 때문에, UI를 두 번 짜는 수고로움은 충분히 감수할 만한 작은 비용에 불과합니다.
  • 초기 세팅 비용은 1회성이지만, 런타임 안정성은 영구적이다:
    Gradle 연동이나 Kotlin-Swift 인터옵 같은 툴링 허들은 프로젝트 초기에 딱 한 번만 제대로 세팅해두면 끝나는 1회성 비용입니다.
    반면 Flutter/RN의 서드파티 플러그인 충돌, OS 업데이트마다 터지는 빌드 에러, 메모리 릭과 GC 랙은 서비스가 운영되는 내내 영구적으로 개발자를 괴롭히는 기술 부채입니다. 1회성 세팅 비용을 치르고 영구적인 안정성을 사는 것이 훨씬 남는 장사였습니다.
  • 크로스 플랫폼의 '가짜 네이티브' 수정 비용보다 UI를 네이티브로 짜는 게 훨씬 빠르다:
    Flutter나 RN에서 OS 특유의 미세한 스크롤 저항감, 햅틱 피드백, Dynamic Island, 백그라운드 위치 추적 등을 억지로 구현하느라 수많은 시간을 삽질해 본 분들이라면 압니다.
    차라리 SwiftUI와 Compose로 깔끔하게 공식 문서를 보며 네이티브 코드를 짜는 것이, 크로스 플랫폼 플러그인을 뒤적거리며 플랫폼 채널을 뚫는 것보다 실제로는 훨씬 빠르고 스트레스가 적습니다.

결국 "감당 가능한 작은 단점(UI 개별 구현, 초기 세팅)을 내어주고, 감당하기 힘든 치명적인 위험(런타임 크래시, 메모리 저하, 로직 불일치 버그)을 완벽히 방어할 수 있다"는 점에서, KMP + Native는 현존하는 가장 영리하고 실용적인 투자였습니다.

마치며: 은총알은 없다, 그러나 가장 단단한 선택

소프트웨어 개발에 모든 상황을 완벽하게 만족시키는 은총알은 존재하지 않습니다.

1~2주 안에 빠르게 시장 반응을 테스트해야 하는 극초기 토이 프로젝트나, OS 고유 기능이 거의 필요 없는 단순 정적 뷰어 앱이라면 Flutter나 React Native가 여전히 빠르고 훌륭한 선택지가 될 수 있습니다.

하지만 내가 만드는 서비스가 장기적으로 운영되어야 하고, 유저에게 단 1ms의 버벅임도 없는 쾌적한 네이티브 경험을 주어야 하며, 복잡한 비즈니스 로직을 안전하게 지켜내야 한다면 이야기는 달라집니다.

"Data와 Domain은 KMP로 단단하게 묶고, Presentation은 각 OS의 순수 네이티브로 유연하게 펼친다."

양대 플랫폼 지원이라는 영원한 숙제 앞에서, 이 조합이야말로 모바일 개발의 생산성과 네이티브의 완성도를 모두 놓치지 않는 가장 단단하고 우아한 최선의 해답이라고 생각합니다.
