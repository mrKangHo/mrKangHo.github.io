양대 플랫폼(iOS/Android)을 지원하는 최선의 방법?

"하나의 코드로 두 마리 토끼를 잡으려다 마주치는 한계, 그리고 내가 'CMP(Data/Domain) + Native(Presentation)' 조합을 선택한 이유"

작성자: 이강호 (Kano — 모바일 파트 리더)

"이번 신규 프로젝트, iOS랑 안드로이드 둘 다 빠르게 내야 하는데 어떤 기술 스택으로 가야 할까요?"

모바일 서비스를 기획하고 개발하는 팀이라면 누구나 마주하는 가장 오래되고도 치열한 질문입니다. 비즈니스의 빠른 시장 검증을 위해서는 iOS와 Android 양대 플랫폼을 모두 지원해야 하지만, 현실의 개발 리소스(인력, 시간, 예산)는 언제나 한정되어 있기 때문입니다.

이때 자연스럽게 가장 먼저 검토되는 선택지가 바로 Flutter나 React Native 같은 크로스 플랫폼 프레임워크입니다. "하나의 코드베이스로 두 플랫폼을 동시에 지원할 수 있다"는 약속은 프로덕트 매니저와 엔지니어 모두에게 거부하기 힘든 달콤한 유혹입니다.

하지만 11년간 다양한 규모의 모바일 프로덕트를 만들고 이끌며 깨달은 것은, 모든 은총알(Silver Bullet)에는 반드시 대가가 따른다는 점이었습니다.

"비즈니스 로직의 중복은 없애고 싶지만, 유저가 매일 손끝으로 만지는 네이티브 특유의 정교함과 메모리 효율, OS 신기능 지원을 포기할 수는 없다. 과연 양대 플랫폼을 지원하는 진정한 최선의 방법은 무엇일까?"

1. 크로스 플랫폼(Flutter, RN): 분명한 장점과 현실적인 한계

Flutter와 React Native는 현대 소프트웨어 생태계에 지대한 공헌을 한 훌륭한 도구들입니다. 저 역시 빠른 MVP 검증이나 SaaS 프로젝트에서 적극적으로 활용해 보았고, 그 생산성에 감탄하기도 했습니다.

장점: 압도적인 출시 속도와 단일 코드베이스

  • Write Once, Run Everywhere: UI부터 비즈니스 로직까지 하나의 언어(Dart 또는 JS/TS)로 작성하여 두 플랫폼에 즉시 빌드할 수 있습니다.
  • 동일한 출시 사이클: iOS 팀과 Android 팀의 기능 배포 일정 차이(스펙 갭)가 사라지고, 소규모 팀으로도 빠른 초기 피봇이 가능합니다.

하지만 서비스의 규모가 커지고, 복잡한 사용자 인터랙션과 고도화된 시스템 기능이 요구되는 프로덕션 단계에 들어서면 다음과 같은 구조적 병목에 직면하게 됩니다.

한계 ①: 무거운 메모리 풋프린트와 런타임 오버헤드

크로스 플랫폼 앱은 순수 네이티브 앱에 비해 기본 메모리 사용량이 필연적으로 높습니다.

  • Flutter: 앱 바이너리 내에 Dart 가상머신(VM)과 자체 그래픽 렌더링 엔진(Skia / Impeller)을 통째로 패키징합니다. 텍스트 몇 줄만 있는 빈 화면을 띄우더라도 기본적으로 상당한 메모리를 점유하며, 복잡한 대량 리스트 스크롤이나 대용량 이미지 처리 시 가비지 컬렉터(GC) 동작에 따른 미세한 프레임 드랍(Micro-jank)을 완전히 피하기 어렵습니다.
  • React Native: JavaScript 런타임(Hermes 등) 구동 오버헤드와 JS-Native 간의 비동기 통신(또는 JSI) 비용으로 인해 CPU 연산과 메모리 압박이 가중되며, 이는 배터리 소모와 기기 발열로 직결됩니다.

한계 ②: '가짜 네이티브'의 장벽과 OS 고유 기능 지원의 지연

Apple과 Google은 매년 WWDC와 Google I/O를 통해 최신 OS 기능과 혁신적인 인터페이스를 발표합니다:

  • iOS: Dynamic Island, Live Activities, 락스크린 위젯, ProMotion(120Hz) 가변 주사율, 정교한 햅틱 엔진, Apple Intelligence API
  • Android: Material You 동적 테마, 예측 뒤로가기(Predictive Back), 세분화된 포그라운드 서비스 및 배터리 최적화 정책

크로스 플랫폼은 이 혁신을 Day 1에 온전히 흡수하지 못합니다. 제3자 오픈소스 플러그인이 업데이트되기를 마냥 기다려야 하거나, 결국 각 플랫폼에 맞춰 MethodChannel이나 네이티브 브리지를 직접 작성해야 합니다.

"결국 네이티브 기능을 쓰기 위해 각 OS 코드를 따로 짜고 있다면, '하나의 코드로 개발한다'는 크로스 플랫폼의 본래 약속은 어디로 간 것일까요? 배보다 배꼽이 더 커지는 상황이 발생하는 것입니다."

2. 내가 선택한 해답: CMP(KMP) + Native 하이브리드 전략

양대 플랫폼을 지원하면서 우리가 진정으로 원했던 가치는 무엇이었을까요?

"서로 다른 두 OS의 화면(UI)을 억지로 붕어빵 찍듯 똑같이 만드는 것"이 아니었습니다. 진짜 우리가 해결하고 싶었던 비효율은 "네트워크 통신, 로컬 DB 캐싱, 비즈니스 검증 규칙, 데이터 가공 로직을 iOS와 Android에서 두 번씩 따로 구현하고 버그를 맞추는 고통"이었습니다.

그래서 저는 가장 균형 잡히고 단단한 조합으로 CMP(Compose Multiplatform / KMP) + Native 전략을 채택했습니다.

핵심 아키텍처 원칙:
• Data Layer & Domain Layer: CMP (Kotlin Multiplatform)로 100% 공유
• Presentation Layer: 각 OS의 순수 네이티브(Jetpack Compose & SwiftUI)로 구현

왜 이 조합일까요? 코틀린 멀티플랫폼(KMP/CMP)은 별도의 가상머신이나 자바스크립트 엔진을 띄우지 않습니다.

Android에서는 네이티브 JVM 바이트코드로, iOS에서는 LLVM 컴파일러를 통해 순수 Objective-C/Swift 바이너리 프레임워크(.xcframework)로 직접 빌드됩니다. 런타임 통신 브리지도 없고, 불필요한 메모리 낭비도 전혀 없는 진짜 네이티브 코드로 동작합니다.

3. 계층별 구현: Clean Architecture를 멀티플랫폼에 녹이다

모바일 CMP + Native 계층 구조 아키텍처 
┌─────────────────────────────────────────────────────────────┐
│                 PRESENTATION LAYER (NATIVE)                 │
│   Android: Jetpack Compose (Kotlin)   │   iOS: SwiftUI (Swift)   │
│   • 120fps 유체 애니메이션             │   • Dynamic Island / 위젯 │
│   • Material 3 인터랙션                │   • HIG 고유 햅틱 및 제스처│
└──────────────────────────────┬──────────────────────────────┘
                               │ StateFlow / ObservableObject
┌──────────────────────────────▼──────────────────────────────┐
│                  DOMAIN LAYER (CMP / SHARED)                 │
│   • UseCases (인증, 결제, 장바구니, 데이터 검증 로직)           │
│   • Domain Models & State Machine (MVI / Redux)             │
│   • 플랫폼 간 비즈니스 규칙 정합성 100% 일치                 │
├─────────────────────────────────────────────────────────────┤
│                   DATA LAYER (CMP / SHARED)                  │
│   • Network Client: Ktor Client (HTTP / WebSocket)          │
│   • Local Storage: SQLDelight / Room KMP                    │
│   • DTO Mapping & Repository Implementations                │
└─────────────────────────────────────────────────────────────┘

① Data & Domain: CMP로 완벽 일원화

  • 네트워크 및 캐싱: Ktor와 SQLDelight / Room KMP를 활용하여 API 통신 및 로컬 캐싱 엔진을 단일 코드로 구축합니다.
  • 도메인 정책: 유효성 검사, 결제 할인율 계산, 상태 머신(State Machine) 등 비즈니스 핵심 규칙을 하나의 코드로 관리합니다.
  • 결과: "iOS에서는 되는데 안드로이드에서는 결제 금액 계산이 다르게 나온다"와 같은 플랫폼 간 비즈니스 로직 불일치 버그가 원천 차단됩니다. 공유 로직에 대한 단위 테스트(Unit Test)를 한 번만 작성해도 양대 플랫폼 전체의 안정성이 검증됩니다.

② Presentation: 각 OS의 순수 네이티브 UI로 작성

  • Android (Jetpack Compose): Google의 최신 디자인 시스템(Material 3), 빠른 리컴포지션, Android 시스템 백버튼 및 제스처에 최적화된 화면을 구현합니다.
  • iOS (SwiftUI): Apple의 Human Interface Guidelines(HIG)를 충실히 반영한 네이티브 네비게이션, Dynamic Island, 실시간 활동(Live Activities), 잠금화면 위젯 등을 단 한 줄의 타협 없이 완벽하게 연동합니다.
  • 상태 구독: CMP 공통 모듈에서 방출되는 Kotlin의 StateFlow를 Android에서는 collectAsStateWithLifecycle()로, iOS에서는 Swift의 AsyncSequence나 @Published 래퍼를 통해 손쉽게 네이티브 상태로 바인딩합니다.

4. 기술 스택 종합 비교

각 접근 방식의 실질적인 트레이드오프를 표로 비교해 보면 CMP + Native 조합의 강점이 더욱 선명하게 드러납니다.

비교 항목 Flutter / React Native Full Native (각각 개발) CMP + Native (채택)
코드 공유율 85% ~ 95% (UI + 로직) 0% (완전 분리) 50% ~ 65% (로직/데이터 공유)
메모리 및 성능 VM/엔진 오버헤드로 다소 무거움 최상 (100% 네이티브) 최상 (런타임 오버헤드 제로)
OS 신기능 지원 플러그인 대기 또는 브리지 작업 필요 발표 당일 즉시 적용 가능 UI가 네이티브이므로 즉시 적용 가능
비즈니스 로직 정합성 단일 코드로 일치 플랫폼 간 오차/버그 발생 위험 높음 KMP 단일 코드로 완벽 보장
유저 사용 경험(UX) 미세한 제스처/물리엔진 이질감 존재 OS 고유의 가장 자연스러운 경험 100% 순수 네이티브 사용성 보장
팀 협업 및 확장성 특정 프레임워크 전담 엔지니어 필요 iOS/Android 팀 완전 이원화 네이티브 엔지니어 역량 극대화 & 공유

5. 모바일 파트 리더로서 느낀 실무 현장의 이점

이 아키텍처를 실무에 도입했을 때 가장 만족스러웠던 부분은 기술적 수치를 넘어 팀의 문화와 엔지니어링 만족도였습니다.

① 네이티브 개발자의 전문성과 자부심 유지

크로스 플랫폼 전환을 시도할 때 네이티브 엔지니어들이 겪는 가장 큰 좌절은 "수년간 쌓아온 OS 전문성이 무의미해지는 느낌"입니다. 하지만 CMP + Native 구조에서는 Android 엔지니어는 Jetpack Compose의 고도화에 집중하고, iOS 엔지니어는 SwiftUI와 Apple 에코시스템의 최신 기술을 마음껏 펼칠 수 있습니다.

② Kotlin과 Swift의 환상적인 시너지

현대의 Kotlin과 Swift는 언어적 문법과 패러다임이 놀라울 정도로 닮아 있습니다. 또한 Jetpack Compose와 SwiftUI 역시 선언형 UI(Declarative UI)라는 동일한 사상을 공유합니다.

덕분에 iOS 개발자가 Kotlin으로 작성된 Domain 로직을 읽고 PR 리뷰를 남기는 데 진입장벽이 거의 없으며, 모바일 파트 전체가 하나의 언어로 아키텍처를 논의하는 진정한 의미의 '원팀(One Team)'이 완성됩니다.

마치며: 은총알은 없다, 그러나 가장 단단한 선택

소프트웨어 엔지니어링에 모든 상황을 만족시키는 완벽한 은총알은 존재하지 않습니다.

1~2주 안에 빠르게 반응을 살펴봐야 하는 초단기 토이 프로젝트나, OS 고유 기능이 거의 필요 없는 단순 조회용 뷰어 앱이라면 Flutter나 React Native가 여전히 훌륭한 선택지가 될 수 있습니다.

하지만 여러분의 프로덕트가 장기적으로 성장해야 하고, 수많은 유저에게 단 1ms의 딜레이도 없는 쾌적한 네이티브 경험을 선사해야 하며, 복잡한 비즈니스 로직을 안전하고 견고하게 유지보수해야 한다면 이야기는 달라집니다.

"Data와 Domain은 CMP로 단단하게 묶고, Presentation은 각 OS의 순수 네이티브로 유연하게 펼친다."

양대 플랫폼 지원이라는 영원한 숙제 앞에서, 이 조합이야말로 모바일 개발의 생산성과 완성도를 둘 다 놓치지 않는 가장 단단하고 우아한 최선의 해답이라고 자신 있게 추천합니다.
